# Purpose

Change EclipseERP persistence through the owning domain, the Drizzle schema graph, reviewed migrations, and database-level invariant checks.

# Use This Skill When

- changing a file under `db/schema/`;
- adding a column to inventory reservations or another owned model;
- creating a constraint, index, trigger, RLS policy, or data backfill;
- creating or debugging a Drizzle migration.

# Do Not Use This Skill When

- only a DTO or API representation changes;
- the current package does not own the target schema;
- the request would rewrite an applied migration.

# Required Context

Inspect:

- [`db/ownership.toml`](../../../db/ownership.toml);
- the owner’s schema file, service, and PostgreSQL tests;
- [`db/schema/index.ts`](../../../db/schema/index.ts), [`drizzle.config.ts`](../../../drizzle.config.ts), and the latest migration snapshots;
- the constraint error mappings in the owning domain.

Use the generic constraint strategy when choosing direct-write, pre-validation, or transactional validation.

# Architecture Rules

- PostgreSQL is transactional truth; constraints are the final correctness boundary.
- Only the owning domain may define or mutate its tables.
- Drizzle owns typed schema/query construction, not the domain model.
- Every migration is generated by pinned Drizzle Kit `1.0.0-rc.4`, includes `migration.sql` and `snapshot.json`, and carries owner, review-date, and generator headers.
- Unsupported DDL starts from a custom Drizzle migration.
- Never rewrite an applied migration; add a new one.
- Map known constraint failures to stable domain errors without exposing SQLSTATE, table names, or driver objects.

# Workflow

## 1. Inspect

Confirm the schema owner and read the existing table constraints, service write path, migration ancestry, and invariant tests.

## 2. Decide

Choose the minimum structural change. Decide which guarantees belong in Effect Schema, domain logic, a transaction, and PostgreSQL. For concurrency-sensitive state, validation and mutation must be atomic.

## 3. Implement

1. Change only the owner’s `db/schema/<schema>.ts` file and export it from `db/schema/index.ts` if new.
2. Run `deno task db:generate --name=<short_name>`.
3. For unsupported DDL, run `deno task db:generate --custom --name=<short_name>` and edit the generated SQL.
4. Add required migration headers without renaming the generated directory.
5. Update the owning service’s typed error mapping and tests.
6. Add a PostgreSQL invariant test when the database enforces behavior that an in-memory layer cannot prove.

## 4. Validate

Review generated SQL and snapshot ancestry before running migration checks. Rehearse against a disposable database when `DATABASE_URL` is available.

# Deterministic Tools

```sh
deno task db:generate --help
deno task db:check
deno task boundary:lint
deno task test
deno task check
```

Use `deno task migrate` only with an explicitly selected database. Do not run destructive or production migration commands without the repository’s existing review and permission controls.

# Required Checks

- ownership headers name registered schemas;
- `snapshot.json` exists and ancestry remains linear;
- generated SQL is schema-qualified and reviewable;
- contract tests cover mapped domain failures;
- database tests cover constraints, triggers, rollback, immutability, or concurrency as applicable;
- applied migration history remains unchanged.

# Failure Conditions

Stop when the requested package is not the registered owner, a migration must be rewritten, generated SQL changes another domain’s objects without multiple declared owners and review, or a safe backfill/rollback strategy is undefined.

# Completion Criteria

The owner’s schema, generated migration graph, service mappings, and invariant tests agree; migration and boundary checks pass; no raw database failure enters a public contract.
